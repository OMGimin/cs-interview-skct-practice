## 구현·검증 근거 (2026-09-25)

- 자동 테스트 27개: 서명/워크스페이스 격리/이벤트 분류/메시지 출력, 학습 상태, 번호 검증, 중복 요청, 오래된 답변·버튼, 동시 요청, 전송 실패 복구, 검수 중단 문항, 기록 정리, 스키마 마이그레이션, 콘텐츠 계산.
- `npm run check`: 타입 검사·테스트·12개 콘텐츠 검사 통과.
- `npm run test:runtime`: dry-run 번들 후 실제 workerd·로컬 D1을 사용. 모든 Slack API 호출은 가상 응답으로 가로채므로 실제 Slack 전송이 아니다. 서명된 HTTP, URL 검증, 두 버튼, CT와 CS 학습 흐름, 재전송 중복 방지, 잘못된 번호, 답변 원문 미보관을 확인.
- Workers 런타임의 기본 fetch 메서드 호출이 Illegal invocation을 일으킴을 재현하고 globalThis에 바인딩해 수정. Node 단위 테스트 통과와 Workers 실행 성공을 별도로 확인했다.
- DB 0001 적용 후 구조를 바꿔야 해서 0002를 추가했다. 기존 모든 attempts 행을 복사하는 마이그레이션을 테스트했고 기존·신규 로컬 DB 적용을 확인했다.
- 콘텐츠는 CS 6·CT 6개. 별도 Sol 검토자가 CS 문서를 대조하고 CT 계산을 직접 확인했다. 사람 검수·실제 SKCT 출제 적합성은 미검증이다.
- 원래 앱 기획서는 수정하지 않았고, 슬랙 기획서에 MVP 결정과 구현 상태를 통합했다.

## 남은 운영 경계

- 실제 Slack 앱 설치·토큰 설정·Cloudflare 배포 및 원격 DB 적용은 수행하지 않았다. Git 원격 반영은 후속 요청에 따라 별도로 진행한다.
- `waitUntil`은 영속 큐가 아니다. 실행 중단 시 사용자의 다음 입력을 통한 재시도가 필요하다. Slack 전송과 D1 갱신은 단일 트랜잭션이 아니므로 전송 성공 뒤 DB 실패/네트워크 타임아웃에서는 중복 메시지가 가능하다.
- 한 워크스페이스의 소규모 파일럿 구현이다. 90일 후 본 문항 기록이 삭제되어 같은 문제를 다시 받을 수 있다. 대량 문제은행의 조회 비용·무료 한도·운영 부하는 실제 배포 환경에서 추가 확인한다.
